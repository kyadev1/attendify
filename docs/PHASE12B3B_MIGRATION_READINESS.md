## Verified contracts

- register_for_event(uuid) derives auth.uid(), requires Student profile role, locks the event FOR UPDATE, requires published status and ends_at > now(), rejects any existing student/event registration, counts registered rows, and inserts one registration. Registration may occur after starts_at while the event is ongoing.
- UNIQUE(event_id,student_id) is unconditional, including cancelled registrations. UNIQUE(id,event_id) already exists and can support the answer-set FK without another index.
- Registration IDs are UUIDs generated by the existing default. The return is public.registrations. Existing QR references use this registration ID; neither QR nor attendance RPC is changed by the proposed feature.
- check_in_ticket verifies organizer ownership/role, published event and matching registered ticket. UNIQUE(registration_id) plus ON CONFLICT prevents duplicate attendance rows. Attendance's composite registration/event FK preserves association.
- RLS is enabled, not forced, on four postgres-owned tables. anon/authenticated are neither superusers nor BYPASSRLS. Profile UPDATE grants cover full_name only, not role; signup trigger hardcodes student.
- Direct authenticated registration INSERT/UPDATE/DELETE is absent at table and column level. Existing registration/attendance RPC execution excludes PUBLIC/anon and allows authenticated/service_role. Definitions use empty search_path and qualified application tables.
- Frontend registration still goes directly through Supabase (`src/services/registrationService.js`). Express remains read-only. No production React/Express integration was modified.

## Findings

**High — excessive privileges, confirmed metadata:** anon/authenticated have effective TRUNCATE on all four tables, plus REFERENCES/TRIGGER and maintenance ACL rights. RLS does not restrict TRUNCATE. The roles cannot log in directly or create schema objects under inspected grants; no arbitrary-SQL HTTP entry point was demonstrated. Do not call this a proven anonymous REST exploit. Migration 001 narrowly revokes unnecessary rights without changing CRUD/RPC permissions. Broad public defaults remain; new objects revoke their default grants within the creation transaction. Managed-schema defaults are not changed indiscriminately.

**High — capacity editing, confirmed definition interaction; runtime untested:** validate_event_capacity is SECURITY INVOKER and counts registrations under a student-only SELECT policy. Organizer edits therefore cannot reliably count actual students. Migration 005 makes this narrow trigger SECURITY DEFINER, preserving its check/message and using empty search_path. Registration admission already has an event lock; staging must verify concurrent capacity updates too.

**High — populated-event deletion, confirmed definition interaction; runtime untested:** the owner delete policy's NOT EXISTS registrations check sees only RLS-visible rows, while deleting an event cascades registrations/attendance. Migration 005 adds a definer BEFORE DELETE guard against actual registrations, leaving the existing RLS policy intact. This prevents the invisible-row interpretation rather than broadening registration reads.

These corrections require independent review and staging tests. The metadata is evidence of definitions, not proof of actual negative authorization or concurrency outcomes.

## Proposed storage decision requiring approval

The draft refines Phase 12B.2's normalized question/choice proposal to **one bounded JSONB definition per immutable version and one validated JSONB answer object per registration**. This reduces migration surface for the existing five-type JSON builder and avoids duplicate authoritative representations. Question/choice membership and required/type/size constraints are enforced in database functions/triggers. If normalized analytics are required now, revise this design before execution; do not deploy competing copies.

- event_registration_forms: event PK, mutable draft, optimistic revision and same-event active-version FK.
- registration_form_versions: UUID, event, monotonic revision, immutable definition, publication time.
- registration_answer_sets: existing registration PK, composite registration/event FK, same-event version FK, immutable answers/time.

New tables have RLS and no direct ordinary-user access. Scoped read/write RPCs enforce ownership/identity. They use narrowly scoped SECURITY DEFINER with qualified tables and empty search_path, owned by postgres; no service-role application client. Private helpers deny schema/EXECUTE access. Defaults are explicitly revoked before intended grants in each transaction.

Versions cannot be individually deleted or updated. Parent-event cascade can remove unused versions, but answer FKs retain submitted history. Erasure of a student/registration with answers will fail rather than silently delete history: retention/deletion policy needs approval before production. No old registrations are backfilled.

SQL uses Unicode code-point lengths, while current JS uses UTF-16 units and JS trim/case behavior. Shared validation must be aligned before UI activation, including whitespace, emoji and locale-sensitive NFKC/case rules. New definitions contain only schemaVersion/questions; eventId is the authorized RPC argument. This draft does not silently modify the existing builder payload.

## Operations and preservation

Draft saving uses expected revision and event-row lock with ownership recheck. Publication uses the same event lock, expected draft revision and active-version comparison; it inserts an immutable version and updates the pointer atomically. Student reads see active published forms only, while answer reads permit only the registration's student or owning organizer, with historical definition.

004 copies the authoritative registration body into a private helper. Local comparison confirms the body is preserved, changing only function name/schema and return qualification. The answer RPC validates active version/answers and inserts registration plus answers in one transaction using the original capacity/duplicate implementation. Failure rolls back both. Return fields, ID, QR and attendance code stay unchanged.

Legacy register_for_event rejects every active version, **including an empty form**, requiring explicit version acknowledgement. No-form events retain their existing path. The guard is independent of the release switch, so disabling UI cannot re-enable bypass. No active forms are created by installation.

Duplicate retries retain the deployed duplicate error; no new idempotency-key system is introduced. Future clients must recover uncertain success by reading their existing booking/answers, not overwrite answers or silently fall back to legacy registration.

Private release state defaults enabled=false. Draft operations can work after installation, but publishing and custom submission cannot. No activation SQL or application integration is supplied.
